# 技術選定の理由（説明ドキュメント 3-3 と、審査軸 1b の材料）

判断ごとに、「候補」「選んだもの」「選んだ理由」「捨てた理由」「限界」を書く。**限界（できていないこと）も書く**（できていないことを「やっている」と書かない）。
事実の確認元は、コード、PR の説明、`web/README.md`。確認できていないことは「未確認」。

## 1. 実行基盤: Cloud Run

| 項目 | 内容 |
|---|---|
| 候補 | Cloud Run／App Engine／Compute Engine／GKE／Firebase Hosting・App Hosting（運営が認める実行基盤） |
| 選んだもの | **Cloud Run**（`asia-northeast1`）。画面と API を 1 つのコンテナで配る（ルートの `Dockerfile`） |
| 選んだ理由 | ① 画面（ビルド済み）と API を、サーバー 1 つ（`server/app.py`）が配る今の構成を、そのままコンテナにできる。② リクエストが無い間は課金されない（最小インスタンス 0）。学生の予算（$20・$300）に合う。③ サービスアカウントで Vertex AI を呼べる（鍵をリポジトリにも環境にも置かない） |
| 捨てた理由 | GKE・Compute Engine: 4 人・数日の開発に対して、運用の負担が大きい。App Engine: コンテナの Dockerfile をそのまま使えるほうが、手元と本番の差が小さい。Firebase Hosting との分離: 余裕があれば検討としたが、1 つで済むので見送った |
| 設定 | 最大インスタンス数 1、CPU は「リクエストの処理中だけ」課金、メモリ 1 GiB、タイムアウト 300 秒（`web/README.md`「Cloud Run に置く」） |
| 限界 | **最大 1 台**にしているのは、プランを作る仕事の進み具合を、サーバーのメモリに持つため（2 台に分かれると見失う）。同時に、費用の上限にもなる。多くの人が同時に使う用途には、状態を Firestore などに移す必要がある（旅の保存は Firestore に入ったが、この仕事の状態はまだメモリ） |

## 2. AI: Gemini（Vertex AI）

| 項目 | 内容 |
|---|---|
| 候補 | Vertex AI の Gemini／Google AI Studio の Gemini API キー／他社の LLM API |
| 選んだもの | **Vertex AI の Gemini**（`server/gemini.py`、`google-genai`）。モデルは Flash 系、考える量は少なめ（`ZT_THINKING=LOW`） |
| 選んだ理由 | ① 運営の規約: プロダクトのメイン技術は Google 技術。他社 AI がコアだと審査対象外。② 配られたクレジット（$20）は Vertex AI にだけ使える（AI Studio には使えない）。③ Cloud Run のサービスアカウントで認証でき、鍵を持たなくて済む。④ Flash 系で、考える量を `LOW` にすると、1 回が速い（`web/README.md`：既定の量では約 2 倍遅い） |
| 捨てた理由 | AI Studio のキー: 手元の開発には使う（無料枠）が、本番には使わない（クレジットが使えず、鍵の管理も要る）。他社の LLM: 規約上、禁止ではないが、Google 技術の活用では評価されない |
| 使い分け | **Gemini に任せるもの**: 候補の収集、混雑の推定、プランへの頼みの解釈、ミッションの作成、スクリーンショットの読み取り。**Gemini に任せないもの**: 時刻の計算と、回る順番（間に合わないスケジュールを作るため。`web/src/lib/planner.ts` が規則で行う）、旅行者の最終的な選択 |
| 限界 | 混雑・営業時間などの推定は、実測ではなく、間違うことがある。画面に「推定」と出し、Google マップで確認できるリンクを添える。Gemini の呼び出しは、1 時間あたりの上限（`ZT_LLM_PER_HOUR`）で、費用と暴走を抑える |

## 3. 地図: MapLibre と Google マップ（Maps JavaScript API）の両対応

| 項目 | 内容 |
|---|---|
| 候補 | MapLibre ＋ OpenFreeMap／Google マップ（Maps JavaScript API）／Leaflet ほか |
| 選んだもの | **キーがあれば Google マップ、無い・通らないときは MapLibre**（`web/src/lib/gmaps.ts`、`GoogleMapView.tsx`、`MapView.tsx`）。同じ受け取り方で、同じものを描く |
| 選んだ理由 | ① Google 技術の活用（審査軸 1）。② キーが無い環境（GitHub Pages のモック、手元の開発）でも動く。③ キーが通らないとき（制限・失効）に、画面が止まらない |
| 捨てた理由 | Google マップだけ: キー・料金に依存し、モックと手元で動かない。MapLibre だけ: Google 技術の活用が弱い |
| 限界 | 経路の線と移動時間（徒歩・車）は、まだ OSRM（OpenStreetMap）。Google の Routes API への移行は、料金の確認が済んでおらず、保留（issue #10） |

## 4. 場所の情報: Places API（New）

| 項目 | 内容 |
|---|---|
| 候補 | Places API／Wikipedia の写真と Gemini の推定のまま |
| 選んだもの | **Places API（New）** で、写真・評価・営業時間を出し、位置を確かめる（`server/gplaces.py`） |
| 選んだ理由 | 写真・営業時間を、Gemini の推定ではなく、Google のデータで正確にできる。**ただし、営業時間は場所の画面に見せるだけで、時間割の計算には、Gemini の推定（取れない時は 9:00〜17:00）を使っている**（2026-11-07 22:22 時点） |
| 規約への対応 | Places の内容は、**地図が Google マップのときだけ**表示する（Google 以外の地図と一緒に使えないため）。サーバーに保存するのは、`place_id`（期限なし）と緯度経度（30 日まで）だけ。評価・営業時間・写真は取っておかない。写真には投稿者名と Google マップの帰属を出す。照合は 1 エリア 1 回、詳細は場所の画面を開いたときだけ。1 時間あたりの上限（`ZT_PLACES_PER_HOUR`） |
| 限界 | 本番で有効（2026-11-07 に、本番の「この付近を検索」が Places の結果を返すのを確かめた）。設定が外れたときは、Wikipedia の写真と Gemini の推定に戻る |

## 5. 公共交通機関: ODPT（公共交通オープンデータ）の時刻表

| 項目 | 内容 |
|---|---|
| 候補 | ODPT の時刻表／駅すぱあとの API／NAVITIME／Google の Routes API（公共交通機関）／個人公開の乗換 API／OpenTripPlanner の自前運用／Gemini の推定 |
| 選んだもの | **ODPT の時刻表**（GTFS ほか）から、バス・電車の本物の便と、目安の移動時間を出す（`server/bus.py`）。使うのは、ライセンスが出典の表示で済むものだけ |
| 選んだ理由 | ① 事業者が公開している時刻表で、出典を表示すれば使える。② 実際の便と、時刻表から計算した目安に近づけられる（式の目安は、実際の約半分になっていた。PR #38）。③ 日本中のエリアに広げられる（PR #52） |
| 捨てた理由 | **駅すぱあと**: 無料のプランは公開の作品に使えず、有料は規約で時刻の使い回しと AI への入力が禁止（PR #38 の調べ）。キーが届くまでの時間も、期限に間に合わない。**Transit API（個人公開）**: JR の路線が欠け、所要時間が 2〜7 倍ずれた（京都駅→伏見稲荷 34 分、実際は約 5 分）。JR のデータは公式の許諾を受けていないと明記されている。**OpenTripPlanner**: 日本の GTFS はバスが中心で、環境づくりも重い。**Gemini の推定**: 作り話の危険が大きい。**NAVITIME・Routes API**: 日本での返り方・無料枠・規約を確かめきれなかった（未確認） |
| 法的・運用上の決まり | 出典（事業者・版・ライセンス）をシートとプランの下に出す。7 日で取り直す。丸ごと取れる形にしない（1 回 3 便まで、回数の上限）。鍵はサーバーだけに置く |
| 限界 | **時刻表があるのは一部のエリアだけ**（PR #52 の表では、金沢・鎌倉・奈良は使える組みなし）。そのときは、電車は OpenStreetMap の路線と駅からの目安（発車の時刻は無い）、バスは式の目安と、Google マップのリンク、乗換スクリーンショットの取り込みに戻る。電車は乗換なしの 1 路線のみ |

## 6. サーバーと画面の技術

| 項目 | 選んだもの | 選んだ理由 | 限界 |
|---|---|---|---|
| 画面 | React 19 ＋ TypeScript ＋ Vite。スケジュールの計算は Web Worker（`planWorker.ts`） | 型で壊れにくく、計算が数百ミリ秒かかっても画面が止まらない | 画面の自動テストは無い（型チェックとビルドのみ） |
| サーバー | Python（標準の `http.server`）。画面と API を 1 つで配る | 依存を最小にし、Cloud Run のコンテナを軽くする。試作から本番までを、一貫して同じ構成で動かせる | 並行処理・認証・ルーティングの機能が無い。大きくするなら、フレームワークに移す |
| データの保存 | **既定は、ブラウザの `localStorage` だけ**（理由・ミッション・写真。サーバーに送らない）。**Google でログインした人だけ、旅（プラン・理由・ミッション）を Firestore に保存**する（`users/{uid}/trips/{tripId}`、本人の uid の下だけ読み書きできるルール、一覧は 50 件まで）。名前・メールアドレスは保存せず、Gemini にログインの情報を渡さない。作り置き（エリアの候補）はサーバーのファイル | 個人の記録を、ログインしない人には、サーバーに置かない。ログインした人には、別の端末でも同じ旅を開けるようにする。保存を自前で作らず、Firebase の Authentication・Firestore を使う（PR #83、`data/auth-and-trips.md`） | ログインしない場合は、端末をまたいだ共有ができず、容量に限りがある。Cloud Run の置き直しで作り置きは消える（審査の前に温める手順を `web/README.md` に書いた）。ログインと旅の保存は、本番で動くのを確かめた（2026 年 11 月 10 日）。ホーム画面のログイン状態での操作は、PR の時点で画面では未確認 |

## 7. 開発の仕組み

| 項目 | 選んだもの | 選んだ理由 | 限界 |
|---|---|---|---|
| CI | GitHub Actions（開発用のリポジトリ）。PR と `main` への push で、型チェック・ビルド・画面の試験・サーバーの試験（369 本）・Dockerfile の組み立て | 壊れた変更を、マージ前に見つける。サーバーの試験は外の API を差し替えるので、鍵が要らず、費用も掛からない | **提出用のリポジトリは、Actions が使えない**ため、CI は開発用リポジトリで回し、最終コードだけを push する（設定のファイル `.github/workflows/ci.yml` は入れる） |
| 費用の歯止め | 呼び出しの上限（Gemini・Places・時刻表）、予算アラート、最大インスタンス数 1 | **予算アラートは通知だけで止まらない**ため、止める手段として、上限を入れた | クォータの引き下げ（Places API の 1 日あたり）は、設定の確認が要る |
| 秘密情報 | `.env`（git に入れない）、Cloud Run の環境変数、サービスアカウント。リポジトリの全履歴を確認した | 公開リポジトリに、鍵が出ないように | — |
| 手元の開発 | AI Studio の API キー（無料枠）でも動く（`.env`） | Vertex AI の準備が無い開発機でも、本番と同じ流れを試せる | 本番は Vertex AI のみ（AI Studio は、クレジットが使えない） |

## 8. テーマ「Own the Why」の設計判断

- **AI は、複数の候補と、それぞれの注意点（欠点）を出す。人が、理由を添えて選ぶ。** 選んだ理由は、旅のあとの振り返りカード（#12、PR #55）で見返す。
- 開いたとき、いきなり答え（ルート）を出さず、**「行きたい場所を選ぶ」画面から始める**（PR #43）。「自分で決めた」ことが、使い始めに伝わるように。
- Gemini が作った文には、記号（✨に近い印）を付けて、AI が作ったと分かるようにする（PR #39）。
